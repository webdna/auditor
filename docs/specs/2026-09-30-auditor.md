# Auditor

> **Status:** draft - **Version:** 0.11 - **Profile:** `_PROFILE.auditor.md`
> Anyone given permission on a Craft site can answer "who changed this, when, from where, and what
> did it say before?" — and "who signed in, who failed to, and who was given access?" — from the
> control panel, without reading log files or the database.

---

## 1. How it works

A site running Auditor keeps **one log of everything that matters for accountability**: every
content change, with the value each field had before and after, and every security event — sign-ins,
failed sign-ins, lock-outs, password changes, changes to someone's groups or permissions, and one
person signing in as another. Support staff open the log, filter it by person, kind of change, date
or where it came from, and open any row to see exactly what changed. With the Pro edition, the same
history appears where people already work: a **History** panel on each entry, asset, product or user,
and an **Activity** view on each user showing what they changed and what happened to their account.

It records changes wherever they come from — the control panel, a form on the site, a scheduled
command, or a background job — and says which. Large batch operations, such as re-saving every entry
after a settings change or an import of a thousand products, are written as **one entry describing
the batch** rather than a thousand, so the log stays readable and the batch stays fast. Fields that
hold secrets or sensitive data can be listed so that the log records *that* they changed but never
*what* to. Entries age out after a set period, and when a person's account is deleted their name
disappears from the log while the record of what happened stays.

**The idea it rests on: auditing must cost the site almost nothing and must never break it.** Changes
are collected while a request runs and written once, together, at the end — and only if the change
itself was committed; a save that fails or is undone leaves no trace. A page that changes nothing does
no auditing work at all. If recording ever fails, the save or sign-in carries on regardless.

It replaces nothing on the pilot site. It is a separate product from the Auditor plugin built
inside the turf5 site, which recorded control-panel saves only, and which stays where it is.
**Rejected:** writing each change the moment it happens (an extra database write inside every save,
and a record of saves that were later rolled back), and handing each change to a background job
(on a site whose job queue stops, the log silently stops too).

**Vocabulary**

| Term | Means |
|---|---|
| Event | One row in the log: one thing that happened, to one thing, by one person, at one time |
| Actor | Who did it. For a command or job with nobody signed in, "System" |
| Subject | What it happened to — the entry that was saved, or the user who was locked out |
| Context | Where it came from: control panel, site, command, or background job |
| Batch entry | One event standing for a large operation over many elements |
| Redacted | Recorded as "changed", with the value deliberately not kept |
| Lite / Pro | The two paid editions. Both record everything; Pro adds the History and Activity views |

## 2. Scope

**In scope**

- Content changes on every kind of element: created, saved (with before and after values for what
  actually changed), deleted, restored, moved in a structure.
- Sign-in events: signed in, signed out, failed sign-in, locked, unlocked, suspended, unsuspended,
  activated, deactivated, email verified, password changed, password reset required, two-step and
  passkey methods added or removed.
- Access events: groups added or removed, permissions changed, made or unmade an admin, group
  created, changed or deleted, one user signing in as another.
- Commerce orders, once completed: line items added, removed or changed, and adjustments changed.
- One batch entry for large operations, which still shows in each affected item's History.
- Redaction, retention, and removing a deleted person's name.
- The log screen (both editions); History and Activity (Pro).
- Settings in a config file; a switch per context and a master switch.

**Out of scope**

| Not doing | Why |
|---|---|
| Undo or restore from the log | Craft's own revisions do this for entries; a second restore path would disagree with them |
| Editing or deleting log rows in the control panel | An editable audit log is not an audit log |
| Page views and reads | Volume would dwarf everything else, and it is analytics, not accountability |
| Importing the turf5 plugin's history | Different product and shape; turf5 can move over later as its own piece of work |
| Per-site copies of a change that Craft propagates to other sites | One change is one event, for the site it was made on |

**Later**

- System changes: project config, plugins installed or removed, settings.
- Export of a filtered view (CSV).
- Alerts — for example on a burst of failed sign-ins or a new admin (a natural Pro feature).
- A dashboard widget.
- Commerce inventory movements (stock changes), which Commerce records as inventory transactions rather than saves.

## 3. User journeys

**Who this is for**

| Group | What they get |
|---|---|
| Support staff and site owners | The log: who changed what, when and from where |
| Editors (Pro) | An item's History where they edit it |
| Administrators (Pro) | A user's Activity: their changes, sign-ins and access changes |
| Developers | Settings, pruning from the command line, and a way to add their own detail |
| Every editor and member | **Affected**: their changes and sign-ins, and the address they came from, are recorded |
| The site's privacy notice | **Affected**: an audit log holding addresses is a disclosure it should make |

**1. "Who unpublished this?"**
   1. A support person opens **Auditor** in the control panel.
   2. They filter by the entry's name, or by "Saved" events in the last week.
   3. The row shows the person, the time, "Control panel" and the site.
   4. They open it: **Enabled — before: Yes, after: No.**

**2. An entry's History (Pro)**
   1. An editor on an entry chooses **History** from the entry's menu.
   2. A panel lists each change, newest first; one publish is one row, with changes to its blocks
      shown beneath it.
   3. A batch re-save appears as one line: "Included in a re-save of 1,240 entries by Sam".

**3. A user's Activity (Pro)**
   1. An administrator opens a user and chooses **Activity**.
   2. **Changes they made** lists what that person changed.
   3. **Account events** lists their sign-ins, failed sign-ins, lock-outs, and who changed their groups
      or permissions — including "signed in as them".

**4. A developer tunes it**
   1. They copy the example config file and list the fields to redact, and turn off recording from
      background jobs because a nightly import is noise.
   2. They set a retention period; old rows are removed automatically, or at once from the command
      line.

**First run - the empty state.** Straight after install the log reads "Nothing recorded yet — changes
and sign-ins appear here as they happen", with a link to the settings documentation. An item's History
with no rows reads "No changes recorded since Auditor was installed", because history before install
was never kept. A user with no Activity says the same.

## 4. Data model

**`auditor_events`** — one row per event

| Field | Type | Notes |
|---|---|---|
| `id`, `uid`, `dateCreated` | | Append-only: no `dateUpdated` |
| `family` | string(16) | `element` · `auth` · `access` |
| `event` | string(32) | `created`, `saved`, `deleted`, `restored`, `moved`, `bulk`, `login`, `loginFailed`, `logout`, `impersonated`, `locked`, …, `groupsChanged`, `permissionsChanged`, `adminChanged` |
| `elementId`, `elementType`, `siteId` | int, string, int | The **subject**. For auth and access rows, the user the event is about. Null for `bulk` (see the side table) |
| `elementLabel` | string(255) | A snapshot, truncated, so a deleted subject still reads well |
| `ownerId` | int, null | A nested entry's owner, so its change rolls up under the owner |
| `actorId`, `actorLabel` | int null, string | Who did it; label is the email at the time, or "System" |
| `impersonatorId` | int, null | Set on every row written while one user is signed in as another |
| `context`, `contextDetail` | string(8), string(255) | `cp` · `site` · `console` · `queue`, plus route, command or job class |
| `ip`, `userAgent` | string(45), string(255) | Web requests only |
| `requestId` | string(36) | Groups every row one request wrote |
| `data` | JSON | Save: `{field: {label, old, new}}`, redacted as `{label, redacted: true}`, Commerce under `lineItems` / `adjustments`. Bulk: `{operation, count, elementType}`. Auth and access: the event's payload |

Indexes: `(elementId, dateCreated)`, `(ownerId, dateCreated)`, `(actorId, dateCreated)`,
`(family, event, dateCreated)`, `(dateCreated)`. No foreign keys — a row outlives its subject and
its actor.

**`auditor_event_elements`** — the elements a batch entry covered

| Field | Type | Notes |
|---|---|---|
| `eventId` | int | FK to `auditor_events.id`, cascade delete (pruning a batch prunes its list) |
| `elementId`, `siteId` | int | Index `(elementId)`, so History finds batch entries |

**Why this shape.** One table, because the log is filtered across families and a person's Activity
mixes them. The subject and actor are stored as ids *and* labels because both can be deleted and the
log must still read. Before and after values are stored as the field's own serialised form, not as a
full snapshot of the element — a snapshot per save would multiply storage by the number of fields
and duplicate Craft's revisions. The batch side table exists so History can find an element in a
batch without searching JSON.

**On deletion.** Deleting a subject changes nothing: rows keep its label. Deleting a **user**
rewrites their rows' `actorLabel` to "Deleted user #&lt;id&gt;" and removes the attempted username
from their failed sign-ins; ids stay. Rows are otherwise removed only by age.

## 5. Rules

**Recording**

| # | Rule |
|---|---|
| BR-1 | Every event is one row in `auditor_events`. Rows are never updated except by BR-26 and never deleted except by BR-25. Nothing in the control panel edits or deletes them. |
| BR-2 | **Recording never breaks the operation.** Any exception in a watcher or the recorder is caught, logged to the `auditor` log category, and swallowed. A missing table (mid-deploy) is the same. |
| BR-3 | Rows are buffered and written in **one batch insert per flush**; a batch row is the exception, inserted on its own (its id keys its element list) with its list, in one transaction with the flush's other rows. Flushes: end of every web and console request, after every queue job (success or failure), and a shutdown-function backstop. |
| BR-4 | **A row belongs to its transaction.** Added while a transaction is open, it is held until the outermost commit and discarded on the outermost rollback. A rolled-back savepoint inside a committed transaction is not detected (Yii raises no event); this is documented, not worked around. |
| BR-5 | All four contexts are recorded, each tagged with its detail. Config `contexts` lists the ones recorded (default all). Config `enabled` (default true) turns all recording off. |
| BR-6 | Drafts, provisional drafts, revisions and propagating saves are never recorded. The canonical save made by applying a draft **is** — it is the publish. |
| BR-7 | A save's diff compares candidates only: the element's dirty fields, plus the tracked attributes for its type (BR-9). A candidate whose before and after serialised values are equal is dropped. A save with nothing left writes no row, unless config `recordNoChangeSaves` is true. |
| BR-8 | **The before-state is read from the stored rows — never by loading the element**: the element's content row and one row per attribute table for its type, and only when it has candidates. The stored form is the field's `serializeValueForDb()` output. A stored value that still differs from the new one is normalised through the field and serialised again before it counts as a change, which settles a value stored in an older shape; relation fields skip this (their stored form is ids). A relation field with **no** content value — an element last saved before Craft 5.3, or before the field joined its layout — takes its stored ids from the `relations` table, as Craft itself does. |
| BR-9 | Tracked attributes per type — entries: `title`, `slug`, `enabled`, `enabledForSite`, `postDate`, `expiryDate`, `authorIds`, `typeId`, `sectionId`; users: `email`, `username`, `fullName`, `firstName`, `lastName`, `admin`, `photoId`; assets: `title`, `filename`, `folderId`, `volumeId`, `alt`; categories and tags: `title`, `slug`, `enabled`; Commerce orders: `orderStatusId`, `paidStatus`, `email`, `couponCode`; products: `title`, `enabled`; variants: `title`, `enabled`, `sku`, `basePrice`, `basePromotionalPrice` — the stored prices in the store of the site saved, because Commerce's `price` is the catalog price after its pricing rules, which a save does not set. A variant's stock is not tracked: Commerce moves stock through inventory transactions, which save no element, and a variant save only refreshes a stored summary of them. Plugin event `EVENT_DEFINE_TRACKED_ATTRIBUTES` adds or removes. |
| BR-10 | Config `redact` lists field handles and attribute names recorded as `{redacted: true}`. Defaults: `password`, `newPassword`, `verificationCode`, `authKey` (Craft 5 has no password field type, so the list is the whole mechanism). Redaction applies to `created` rows, save diffs and event payloads alike. |
| BR-11 | A new element writes `created` with the non-empty values of its fields and tracked attributes, after redaction. |
| BR-12 | A nested entry's row carries `ownerId`, and shares its owner's `requestId`. |

**Batches**

| # | Rule |
|---|---|
| BR-13 | **An operation is a batch** when it is a resave (`resaving` set, the `resave/*` commands), runs in a batched element job, or is an element-index action on more than one element (on one, it is that element's own row) — or when one Craft bulk operation touches more than `bulkThreshold` top-level elements (default 10). A nested element counts as its immediate owner, never toward the total on its own, so re-saving only one field's nested entries is a batch over their owners. Craft opens a bulk operation around every single save, so a bulk operation alone is not a batch. |
| BR-14 | A batch writes **one** `bulk` row: operation (`resave`, `create`, `save`, `delete`, `restore`, `move`, the action's class or the job's class), element type (null when mixed), count, actor and context. It takes **no before-snapshots and writes no per-element diffs**; when the threshold is crossed mid-operation, rows already buffered for it are folded into the batch row and their diffs dropped. A batched job Craft splits over several queue runs writes one batch row per run that recorded anything (a run is a request of its own, and Craft fires no event when a later run resumes the operation). Config `recordBulkDiffs` (default false) records per-element rows instead. |
| BR-15 | Every top-level element a batch covered — for a nested one, its owner — is listed once per site in `auditor_event_elements`, written in the same flush, so each element's History shows the batch. |

**Sign-in and access**

| # | Rule |
|---|---|
| BR-16 | `login` on every sign-in; remember-me cookie sign-ins only when config `recordCookieLogins` is true (default false). `logout` before the session ends. |
| BR-17 | `loginFailed` records the attempted username and Craft's reason, never the password. The reason is the one Craft refused the account for (`account_locked`, `account_cooldown`, …), not the `invalid_credentials` that `preventUserEnumeration` shows the visitor instead. `actorId`/`elementId` are set only when the username matches a real user. A wrong two-step code counts toward Craft's lock-out but raises no failure event, so it writes no `loginFailed` row; the lock it causes writes `locked`. |
| BR-18 | `locked`, `unlocked`, `suspended`, `unsuspended`, `activated`, `deactivated` are written from Craft's user-service events, because none of them saves the user. `emailVerified` is written when a pending address becomes the account's address, read from the user record's update: `Users::verifyEmailForUser()` fires no event, and the service's `afterVerifyEmail` fires when any verification link is opened (a password reset's too), before anything is verified. |
| BR-19 | `passwordChanged` and `passwordResetRequired` are written without any value. `adminChanged` and `emailChanged` are written as their own access and auth rows, as well as appearing in the user's save diff. All four are read from the user record's update, whose old values cost no query and which every writer passes through; a new account's record is inserted, so creating one writes none of them. |
| BR-20 | `groupsChanged` records `{added, removed}` group handles, and is written only when one was added or removed. `permissionsChanged` records the user's own new set, and the old set when it was readable before the save — the control panel's permissions screen is announced first, so it is read there — and a save that changed nothing writes no row; when the old set was not readable (any other caller), the row has only the new set and is marked `partial`. `groupSaved` records the group, whether it is new, its changed name, handle and description, and its `permissions` `{added, removed}`: Craft saves a group's permissions after the group, as a change of their own, and both halves of one save are one row. Both are read from project config's change events, which carry the old value, so a group changed by applying project config on a deploy is recorded too. `groupDeleted` records the group. A group row has no subject id (a group is not an element); it is named in the label and the payload. |
| BR-21 | `mfaEnabled`, `mfaDisabled`, `passkeyAdded`, `passkeyRemoved` are written only when Craft's action succeeded. `mfaEnabled` is written when Craft stores the authenticator app's secret, which it does only once the first code is verified; signing in with it writes none. `passkeyAdded` and `passkeyRemoved` come from the passkey record, which Craft writes only once the credential is verified and which `Auth::deletePasskey()` deletes; signing in with a passkey writes neither. `mfaDisabled` compares who has an authenticator before and after the two actions that remove one — the control panel's `auth/remove-method` and the `users/remove-2fa` command — because the removal is a bulk delete that fires nothing; a test pins both actions (TN-16). Two-step methods a plugin registers are not recorded. When nobody is signed in (setting two-step up while signing in), the person is the actor as well as the subject. |
| BR-22 | **Subject and actor are distinct.** On auth and access rows the subject is the user it is about and the actor is who did it. `impersonated` is written when one user signs in as another, and every row in that session carries `impersonatorId`. |

**Commerce**

| # | Rule |
|---|---|
| BR-23 | Orders are recorded only once completed; carts are never recorded — not a cart's creation, saves or deletion, nor anything saved or deleted inside a cart's own save (its addresses) — and a cart is skipped before any snapshot is read, so filling one costs the log nothing. The save that completes an order is its first row, a `saved` row showing what completion changed (its status). A completed order's save row also carries `lineItems` (`added`, `removed`, `changed` on purchasable, SKU, quantity, sale price, options, note, private note, status) and `adjustments` (type, name, amount, included, and the line item it applies to), each item under its label (a line item's description, an adjustment's name). Both sides are read from Commerce's tables, before the save and after it, two reads each. Line items are matched by id; adjustments by id and then by type, name and line item, because Commerce writes an order's adjustments again under new ids when it recalculates. A line item status is recorded by name. With Commerce absent, nothing Commerce-related is attached or loaded; with it, Commerce's classes are still never loaded on the log's account. Other elements Commerce saves while a cart is in use — the customer account `setEmail()` creates, the store's location address made on first use — are not the cart's and are recorded as any element is. |
| BR-24 | Plugin event `EVENT_DEFINE_ELEMENT_SNAPSHOT` lets any code add its own keys to an element's row. It is raised, only while someone listens, before a save (the handler reads each key's stored state) and after it with what was read (the handler gives each key's state now); a key whose two states differ is recorded as `{label, old, new}` like a field, or the handler words the change itself — `{label, old, new}`, or a list of items `{label, fields, added, removed, changed}`, which the detail screen draws as a table — and an empty change means none. A new element's call has an empty before. Handler keys are redacted by `redact` like any other value; a list's field labels are never redacted. The Commerce order differ is built on it. |

**Retention and personal data**

| # | Rule |
|---|---|
| BR-25 | Config `retentionDays` (default 365; 0 keeps forever). Older rows are removed by Craft's garbage collection and by `auditor/prune`, in batches of 10,000; a batch row's list of elements goes with it. `auditor/prune --days=N` removes past N days once instead, and refuses N below 1 rather than read 0 as "everything" or "nothing". |
| BR-26 | Deleting a user rewrites their rows' `actorLabel` to "Deleted user #&lt;id&gt;" and clears the attempted username on failed sign-ins against them. `auditor/anonymise-actor` does the same for a given user id. The moment is the deletion **to the trash** — Craft's garbage collection later purges a trashed user with no event — so a user restored from the trash stays anonymised. The rewrite waits for the deletion's transaction to commit (a rolled-back deletion rewrites nothing) and runs after the request's own rows are written, so a row the user made earlier in the same request is rewritten too. It runs whatever the recording settings, because the rows it rewrites were recorded elsewhere. The label is stored in English, like "System". Only the actor is rewritten: rows **about** the user (their sign-ins, their group changes, their deletion) keep the subject label, as for any deleted subject (§4). `auditor/anonymise-actor` refuses a user who still exists, because the rewrite cannot be undone. |
| BR-27 | `ip` and `userAgent` are stored for web requests and shown only to holders of `auditor:viewNetwork`; to anyone else they read "—". |

**Control panel and editions**

| # | Rule |
|---|---|
| BR-28 | Permissions: **Access Auditor** (`accessPlugin-auditor`, Craft's own) opens the log, `auditor:viewNetwork`, and on Pro `auditor:viewHistory` and `auditor:viewUserActivity` — the two Pro permissions are offered for granting only while the plugin is Pro. Craft refuses every control panel address under the plugin's handle to anyone without Access Auditor, and hides the nav item from them, so a separate view-log permission could never open the log on its own; the log's action addresses, which Craft does not guard that way, check the same permission. Admins hold all. No permission lets anyone change a row. |
| BR-29 | The log screen filters by family, event, element type, actor, context, site and date range; its search matches subject and actor labels only. It pages by key (no total count over the table). |
| BR-30 | **Nothing logged is rendered unescaped.** Values longer than 500 characters are truncated with a control to show the rest. |
| BR-31 | History (Pro) lists the element-family rows whose subject or owner is the element, plus batches that listed it, grouped by request; sign-in and access rows about a user are Activity's (BR-32), not History's. In a request, a nested element's row sits beneath the element's next own row, so a request that published twice reads as two publishes. A page never ends inside a request. A batch reads as the element's part in it ("Included in a re-save of 1,240 entries"). It is offered to holders of `auditor:viewHistory`, and answers only for an element they can view; a row's detail opens from History only when the row is in that element's History. The menu item names the canonical element and is not offered on an unpublished draft or an excluded element type. |
| BR-32 | Activity (Pro) is one of Craft's own user edit screens, with two tabs, each paged by key: "Changes they made" — the rows the user is the actor of, except their own account events — and "Account events" — the auth and access rows whose subject is the user, whoever the actor (a failed sign-in, "signed in as them", a group change). So every row is on one tab at most: a user's own sign-in is an account event, and an administrator changing their groups is on the user's Account events and on the administrator's Changes. A user group someone saved has no subject and is a change they made; a save of the user's profile is its History, not an account event; rows written while someone was signed in as the user are the user's changes, marked "Signed in by someone else". It is offered to holders of `auditor:viewUserActivity`, and another user's Activity also needs Craft's `viewUsers`, as every user screen does; a user's own does not. The permission is the whole gate: the rows, and their details, are shown whatever elements they name (a subject the viewer cannot view has no link). A row's detail opens from Activity only when the row is in that user's Activity. |
| BR-33 | **Both editions record identically.** Pro is enforced on both halves: on Lite the History and Activity entry points are absent and their endpoints answer 403. |

**Speed**

| # | Rule |
|---|---|
| BR-34 | A request that saves no element and raises no sign-in or access event adds **zero** database queries. |
| BR-35 | A single element save adds at most one read of its content row joined to its attribute tables, one read per attribute stored elsewhere (an entry's authors, an asset's per-site alt), and none when it has no candidates; plus, for each changed relation field, the ids query its own serialisation runs; plus one read of the `relations` table when a candidate relation field has no content value (BR-8); plus its share of the request's one batch insert. |
| BR-36 | Re-saving 1,000 entries takes at most 10% longer with Auditor enabled than disabled. |
| BR-37 | History and Activity load when opened, never as part of rendering the edit screen. |

**Platform**

| # | Rule |
|---|---|
| BR-38 | Craft `^5.6`, PHP `^8.2`. No code or name specific to any one site. Composer metadata is Plugin Store valid. |
| BR-39 | Schema version starts at 2.0.0 and the tables are created by an idempotent migration as well as by install, so replacing turf5's same-handle plugin creates them. turf5's `auditor_log` table is never read, changed or dropped. |

**Non-functional**

- Nothing is sent. Auditor sends no email, notification or webhook in this version.
- Accessibility: the screens are built from Craft's own control-panel components and inherit their
  keyboard and screen-reader behaviour.
- The log holds personal data (addresses, email addresses, and field values). Redaction, retention
  and deleted-user handling are its controls; each site's privacy notice is the site's to update.

**Plugin events** (in `webdna\auditor\events`): `EVENT_DEFINE_TRACKED_ATTRIBUTES` (BR-9),
`EVENT_DEFINE_ELEMENT_SNAPSHOT` (BR-24), and `EVENT_BEFORE_RECORD`, raised per row before buffering,
which may change the row or set `isValid = false` to skip it.

**Config file** `config/auditor.php`: `enabled`, `contexts`, `excludeElementTypes`, `redact`,
`retentionDays`, `bulkThreshold`, `recordBulkDiffs`, `recordNoChangeSaves`, `recordCookieLogins`.
No CP settings screen — settings are code, deployed like the rest of the site.

## B3. Guardrails

- **Do not diff from `getDirtyFields()` alone** — a site form re-posting every field then logs edits
  nobody made, and AC-2 fails.
- **Do not load the element to get the before-state** — that is a full element query plus field
  normalisation per save, which breaks BR-35 and makes every CP save slower.
- **Do not read dirty state after `EVENT_AFTER_SAVE_ELEMENT`** — `markAsClean()` has already wiped it
  and every diff comes back empty.
- **Do not write rows inside the save** (no insert in a watcher) — it adds a query to every save and
  records saves that later roll back.
- **Do not let any exception escape a watcher or the recorder** — auditing would then break the
  site's saves and sign-ins, the one thing BR-2 forbids.
- **Do not skip the draft guards** — a provisional draft deleted on publish would log as a real
  deletion, and autosaves would flood the log.
- **Do not render any logged value with `raw`** — field content is user input; that is stored XSS in
  the control panel of every customer site.
- **Do not create the tables only in `Install.php`** — replacing turf5's same-handle plugin skips
  install and the plugin then has no table.
- **Do not reference any site's classes, handles or plugins** — the product is sold to sites that
  have none of them.
- **Do not snapshot or diff inside a batch** — a 1,000-entry resave then pays 1,000 before-reads and
  AC-14 fails.
